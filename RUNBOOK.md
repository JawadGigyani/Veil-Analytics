# Veil Analytics Local Runbook

This file explains exactly what is a placeholder, what is generated locally, and what you need to run.

## Required Supabase Values

Your Next.js file is:

```text
privacy-analytics-platform/.env.local
```

It must contain these three values:

```env
NEXT_PUBLIC_SUPABASE_URL=https://lnueehnlkoeayncclocv.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=sb_publishable_your_publishable_key
SUPABASE_SERVICE_ROLE_KEY=sb_secret_your_server_secret
```

The first two come from Supabase Project Settings -> API Keys. The third is the server-only secret key. Keep it in `.env.local`; never rename it to a `NEXT_PUBLIC_` variable.

## Values You Do Not Need To Find Online

These are local application values, not Supabase values:

- `ENCRYPTION_KEY`: generated by the setup script. It encrypts Parquet bytes before storage.
- `WORKER_TOKEN`: generated by the setup script. It is a shared password between Next.js and FastAPI.
- `STORAGE_ROOT`: local fallback directory. Keep `.veil-storage` unchanged.
- `MAX_UPLOAD_BYTES`: upload limit in bytes. Keep `25000000` unless you need a different limit.
- `STORAGE_BUCKET`: Supabase bucket created by `migration-002-platform-features.sql`. Keep `protected-datasets` unchanged.
- `ANALYTICS_WORKER_URL`: local FastAPI address. Keep `http://localhost:8080`.
- `ANALYTICS_WORKER_TOKEN`: automatically set to the same generated value as `WORKER_TOKEN`.

Do not manually invent these values. Run the setup script.

## One-Time Setup

From PowerShell:

```powershell
Set-Location -LiteralPath "H:\New folder (4)\Vermont\privacy-analytics-platform"
python -m pip install -e .\services\analytics-worker
powershell -ExecutionPolicy Bypass -File .\scripts\setup-local.ps1
```

The first command installs the Python worker. The second command generates the Fernet key and worker token, writes `services/analytics-worker/.env`, and adds the matching worker settings to `.env.local`.

## Apply Database Migrations

In Supabase SQL Editor, run these in order:

1. `supabase/schema.sql` if the project is new.
2. `supabase/migration-001-real-records.sql`.
3. `supabase/migration-002-platform-features.sql`.
4. `supabase/migration-003-rate-limits.sql`.
5. `supabase/migration-004-privacy-hardening.sql`.
6. `supabase/migration-005-permissions-audit.sql`.

The `No rows returned` message is normal for DDL statements. It means the schema changed successfully; it does not mean data was supposed to be returned.

Migration `005` is required for dataset permissions, dataset revocation (`revoked_at`), and query hash tracking. If you already applied it, skip this step.

Open two PowerShell windows.


## First Login Flow

1. Create an account or sign in.
2. Confirm your email if Supabase email confirmation is enabled.
3. Sign in again after confirmation.
4. The app bootstraps the organization and demo dataset.
5. The app seeds 1,200 synthetic records into an encrypted Parquet object via the worker.
6. Run `Count records`, `Compare groups`, `Find an average`, or `Build a histogram`.

## Local Demo Checklist

Use this after worker + Next.js are both running:

1. `Invoke-RestMethod http://localhost:8080/health` returns `ok`.
2. Sign in at `http://localhost:3000` and wait for bootstrap to finish without errors.
3. Run a count query and a grouped count; results should report the Laplace mechanism.
4. Confirm remaining epsilon decreases in the privacy budget rail / ledger.
5. Submit a query whose epsilon exceeds the remaining budget and confirm rejection.
6. Invite an analyst from Team access if testing two users; they receive `run_queries` on protected datasets automatically.
7. Owners/admins can open Audit log; analysts without `view_audit_log` cannot.

Gaussian releases are intentionally disabled in this demo until delta accounting is complete.

## CSV Upload Flow

1. Open `Datasets` in the left navigation.
2. Enter a dataset name.
3. Select a CSV file.
4. Enter public clipping bounds for numeric columns as JSON, for example `{"age":[18,90],"score":[0,100]}`.
5. Enter public category domains for grouped fields, for example `{"region":["north","south","east","west"]}`.
6. Confirm that one uploaded row represents one person. Files with repeated rows per person require contribution limiting before ingestion.
7. Click `Upload protected dataset`.
8. Next.js checks your owner/admin role.
9. FastAPI parses CSV or validates Parquet.
10. FastAPI encrypts the normalized Parquet bytes with Fernet.
11. The encrypted object is uploaded to the private Supabase bucket.
12. Only schema metadata, owner-supplied public bounds/domains, and the storage key are saved in Postgres.
13. The uploaded dataset becomes queryable through the Python DuckDB worker.

The browser never receives raw records or a public storage URL.
Numeric columns without valid public bounds remain unavailable for means, sums, and histograms. Grouped count and top-k require public category domains. Veil does not derive public bounds or released category domains from private file contents.

## Benchmark Command

The benchmark command must run in the Python worker directory and needs a Parquet file. It is not a Supabase command.

```powershell
Set-Location -LiteralPath "H:\New folder (4)\Vermont\privacy-analytics-platform\services\analytics-worker"
veil-benchmark .\path\to\data.parquet --epsilon 0.1,0.5,1,2
```

If the command is not found, use:

```powershell
python -m app.benchmark .\path\to\data.parquet --epsilon 0.1,0.5,1,2
```

It creates `benchmark-report.json` and `benchmark-report.md` in the current directory. The input file can be produced by uploading a CSV and converting it with the worker, or by using any local Parquet dataset with numeric columns.

## Live Supabase Test

This is an opt-in automated check against your actual hosted Supabase project. It is not a command required to run the app.

In PowerShell, from the worker directory:

```powershell
$env:RUN_LIVE_SUPABASE_TESTS="1"
$env:SUPABASE_URL="https://lnueehnlkoeayncclocv.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY="paste-your-current-server-secret-here"
python -m pytest -q -m live
```

You only need to change the URL if you use another Supabase project. You must paste the current server secret into the temporary PowerShell environment variable. It is not written to a file by this command.

Expected result after `migration-002-platform-features.sql`:

```text
1 passed
```

If it fails with a missing bucket or table, rerun the migration and inspect Supabase Storage -> Buckets and Table Editor.

## Complete Verification Sequence

Run this sequence after setup:

```powershell
Invoke-RestMethod http://localhost:8080/health
npm test
npm run lint
npm run build
python scripts/run_tests.py
```

`scripts/run_tests.py` runs all three Python suites from their own package
roots. Running `pytest` from the repository root mis-resolves the `app` and
`dp_core` imports, and running it from one package directory silently skips the
others. Install the test dependencies first:

```powershell
pip install -e "packages/dp-core[dev]"
pip install -e "packages/query-ir[dev]"
pip install -e "services/analytics-worker[dev]"
```

Without the `[dev]` extra, `hypothesis` is missing and the property-based
suites fail at collection rather than reporting as skipped — the run looks
smaller rather than broken.

Then perform the browser flow:

1. Sign in.
2. Run a count query.
3. Confirm the privacy budget decreases.
4. Refresh the browser and confirm the ledger remains.
5. Upload a CSV as owner.
6. Query the uploaded dataset.
7. Run a grouped count and confirm each group row shows an uncertainty range.
8. Run a bounded mean on a small filtered population and confirm the composer
   warns before submission that the result will be uninformative.
9. Open Release history and confirm the query appears with its epsilon cost.
10. Open the Audit log and confirm a `query.released` event is recorded, with
    no filter values in the details column.
11. Download the privacy report and confirm `budget_reconciliation.all_reconciled`
    is `true`.
8. Invite an analyst.
9. Change a member role.
10. Switch organizations/datasets if you have more than one.
11. Test password reset.

## Current Status

The local MVP and worker are implemented and local tests pass. Live hosted verification still requires you to run the worker and the live test because this environment cannot reliably exercise your browser session or your Supabase account interactively.

Production rate limiting uses the shared Supabase `rate_limit_events` table after `migration-003-rate-limits.sql`. Redis remains a valid higher-throughput replacement if you deploy at larger scale.
